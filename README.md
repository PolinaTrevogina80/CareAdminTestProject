Roadmap: Архитектурный рефакторинг CareAdminTestProject

1. Декомпозиция слоя шагов (Steps) и паттерн Fluent InterfaceСейчас один гигантский класс 
Steps содержит в себе всё: от заполнения форм инцидента до загрузки файлов и проверок подписей. 
Это усложняет поддержку.
Что сделать: Разбить Steps на логические подклассы по зонам ответственности системы.
Улучшение: Сделать методы «текучими» (Fluent API), чтобы они возвращали this. 
Тогда в самом тесте шаги будут писаться красивой цепочкой:csharpawait steps.IncidentCreation.FillGeneralTabAsync(data)
           .FillDetailsTabAsync(data)
           .ClickCreateIncidentAsync();

2. Оптимизация авторизации (API-driven Auth)
Каждый тест, который логинится через UI, тратит драгоценное время. Тесты сами по себе тяжелые, а с логином через UI еще тяжелее
Если тестов уже 100+, и сборка будет идти вечно.
Что сделать: Оставить один UI-тест на проверку формы логина.
Для всех остальных тестов реализовать получение токена/кук через прямой POST-запрос к API авторизации.
Реализация в Playwright: Использовать IAPIRequestContext для выполнения запроса в блоке [SetUp],
а затем прокидывать полученное состояние (Storage State) в контекст страницы.
Тест будет стартовать уже авторизованным прямо на нужной странице.

3. Ликвидация хардкода и управление конфигурацией
Зависимость от закомментированных строк для смены стендов и захардкоженные тестовые пользователи (targetUserId = "Test, Polly"),
потенциально, причина нестабильности тестов в CI/CD.
Что сделать: Задействовать файл testEnvironments.json.
Настроить чтение конфигурации через Microsoft.Extensions.Configuration.
Что вынести в конфиг:
- BaseURL (Localhost/ Dev / QA / Staging стенды).
- Учетные данные (Логины/Пароли) для разных ролей (DNS, MD, Admin).
- Специфичные ID фасилити (Facility ID), чтобы тесты могли запускаться на любой чистой базе данных.

4. Внедрение стратегии управления тестовыми данными (Test Data Management) и Data Driven подхода
Система имеет жесткие бизнес-ограничения: инцидент можно создать только на реального резидента,
строго в рамках дат его размещения и с валидными справочными типами травм.
Использование случайных данных (рандомизации) здесь невозможно.
Что сделать: Реализовать слой динамического поиска данных в блоке инициализации тестов ([SetUp]).
Реализация:
- Написать SQL-запросы (через Dapper или EF Core) или использовать существующие API-эндпоинты системы, чтобы перед стартом теста вытянуть из базы «свежего» резидента.
- Критерии выборки в запросе: Status = 'Active', AdmissionDate <= CurrentDate, отсутствие блокирующих инцидентов на текущую неделю.
- Тест на лету получает валидный ResidentID, Имя и Фамилию резидента, и динамически рассчитывает дату инцидента под него.
Результат: Тесты перестанут зависеть от жесткого хардкода в коде методов,
но при этом гарантированно будут использовать только валидные, существующие в БД комбинации, не нарушая бизнес-логику системы.
